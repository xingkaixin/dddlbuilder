# 表设计区本地撤销/重做评估（klip-14）

## 背景与现状
- 现有版本能力主要是已保存表维度（如 `VersionHistoryDialog`），非当前编辑会话内的即时撤销。
- 高频编辑场景集中在 `src/components/App/DataTable.tsx` 与相关 stores。
- 目标是评估“内存级历史栈”对建表效率与容错体验的价值。

## 待解决问题
- 用户误删字段、误改配置后无法快速回退最近操作。
- 跨面板（字段、索引、分区、分片）编辑缺少统一撤销语义。

## 拟新增 API / 接口 / 类型草案
- `UndoSnapshot`
- `UndoStackState`
- `pushSnapshot()`
- `undo()`
- `redo()`

## 候选方案
### 方案 A：仅在 DataTable 内做局部撤销
- 优点：实现直观。
- 缺点：无法覆盖跨 tab 操作。

### 方案 B：基于 Zustand 的工作区快照栈（推荐）
- 优点：可统一字段/索引/分区等编辑域，语义一致。
- 缺点：需要定义快照粒度与去重策略。

### 方案 C：基于命令模式记录操作
- 优点：理论上更细粒度。
- 缺点：实现复杂，学习成本高。

## 影响面
- 组件：`src/components/App/index.tsx`、`src/components/App/DataTable.tsx`
- Store：`src/stores/*`（尤其 field/index/partition/sharding）
- Hooks：可能新增 `useUndoRedo` 或工作区历史 hook
- 服务：无直接影响
- 测试：单测 + 强交互组件测试 + 相关 E2E
- i18n：可能新增撤销/重做提示文案

## 风险与依赖
- 风险：快照过大导致内存占用上升；回退边界不一致导致认知混乱。
- 回归面：字段增删改、索引同步、分区配置、导入 SQL 后回退。
- 依赖：当前 persisted state 结构一致性。

## 评估矩阵
| 维度 | 评分(1-5) | 说明 |
|---|---:|---|
| 收益 | 5 | 对高频编辑体验提升非常直接 |
| 复杂度 | 3 | 关键在快照策略与边界定义 |
| 风险 | 3 | 主要是语义一致性与性能 |
| 可逆性 | 4 | 可先灰度在字段域 |

## 验收口径（评估 DoD）
- 明确快照结构、触发时机、最大栈深与去重策略。
- 明确“跨 tab 是否共用历史栈”的规则。
- 定义关键验证场景：误删、批量改、导入后回退。
- 输出是否立项实现及推荐范围。

## 下一步决策项
- Go：快照策略清晰且内存开销可控。
- Hold：先补采样（编辑频率、快照大小）再决策。
- Drop：若复杂度明显超过预期收益。
