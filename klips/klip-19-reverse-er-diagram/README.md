# 反向工程 ER 图能力评估（klip-19）

## 背景与现状
- 现有 `ImportSqlDialog`（`src/components/ImportSqlDialog/index.tsx`）已支持 SQL 导入解析。
- 解析结果可得到表、字段、索引等信息，但尚未可视化为关系图。
- 目标是评估“多表导入后自动生成简易 ER 图”的可行性与范围。

## 待解决问题
- 缺少多表关系可视化视图，结构理解与沟通效率受限。
- 需要评估关系识别准确度、布局策略、交互复杂度。

## 拟新增 API / 接口 / 类型草案
- `ERNode`
- `EREdge`
- `ERLayoutOptions`
- `buildErGraph(parsedTables)`

## 候选方案
### 方案 A：静态只读 ER 预览
- 优点：实现简单，快速验证价值。
- 缺点：交互能力有限。

### 方案 B：基于 React Flow 的最小可交互 ER 图（推荐）
- 优点：可拖拽、缩放、节点聚焦，用户感知更强。
- 缺点：需要额外依赖与布局/性能评估。

### 方案 C：完整建模器
- 优点：能力上限高。
- 缺点：远超当前阶段目标。

## 影响面
- 组件：新增 ER 图容器与图节点组件
- Store：可选新增 ER 视图状态
- Hooks：图数据构建与布局 hook
- 服务：可能复用现有解析服务，无强制新增
- 测试：图数据构建单测 + 基础交互 E2E
- i18n：图视图文案与提示

## 风险与依赖
- 风险：关系推断不准会影响可信度。
- 回归面：导入流程、解析结果兼容性、性能（大表数量）。
- 依赖：图组件库与布局算法选择。

## 评估矩阵
| 维度 | 评分(1-5) | 说明 |
|---|---:|---|
| 收益 | 4 | 可视化价值高，演示效果强 |
| 复杂度 | 4 | 涉及解析扩展、图布局、交互 |
| 风险 | 4 | 准确性与性能是核心风险 |
| 可逆性 | 3 | 新模块可隔离，但投入不低 |

## 验收口径（评估 DoD）
- 明确首期关系识别规则（主外键/命名推断边界）。
- 明确首期图交互范围（只读或可拖拽）。
- 给出大规模节点场景性能门槛。
- 输出 Go/Hold/Drop 与推荐阶段。

## 下一步决策项
- Go：关系识别准确率与性能可达标。
- Hold：先补多表导入与关系识别基线。
- Drop：若当前阶段优先级不足。
