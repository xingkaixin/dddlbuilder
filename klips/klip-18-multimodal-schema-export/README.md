# 结构产物多模态导出评估（klip-18）

## 背景与现状
- 当前 `src/hooks/useSqlGeneration.ts` 主要生成 DDL/DCL，并在 `src/components/App/DDLOutput.tsx` 提供复制操作。
- 尚未提供 Markdown 数据字典与 ORM Model 导出。
- 导出链路具备基础数据源（表结构、索引、注释），可评估扩展。

## 待解决问题
- 产物类型单一，无法直连 Wiki/代码仓 ORM 层。
- 需要评估统一导出框架，避免新增格式时重复拼接逻辑。

## 拟新增 API / 接口 / 类型草案
- `ExportFormat`
- `ExportArtifact`
- `ExporterStrategy`
- `exportSchema(format, payload)`

## 候选方案
### 方案 A：先支持 Markdown 数据字典
- 优点：最快落地，用户价值直接。
- 缺点：ORM 导出延后。

### 方案 B：建立可扩展导出策略层（推荐）
- 优点：可持续支持 Markdown/Prisma/Gorm/JPA。
- 缺点：首期设计需克制，避免过度抽象。

### 方案 C：仅提供后端导出 API
- 优点：前端逻辑轻。
- 缺点：当前项目结构下会引入额外接口复杂度。

## 影响面
- 组件：`src/components/App/DDLOutput.tsx`、可能新增导出对话框
- Store：读取现有表结构状态
- Hooks：扩展 `useSqlGeneration` 或新增 `useSchemaExport`
- 服务：可选（首期可前端本地生成）
- 测试：导出格式快照测试、E2E 导出交互
- i18n：导出格式名称、提示文案

## 风险与依赖
- 风险：多格式语义不一致导致维护压力。
- 回归面：字段类型映射、默认值表达、索引表达一致性。
- 依赖：类型映射规则与数据库差异处理。

## 评估矩阵
| 维度 | 评分(1-5) | 说明 |
|---|---:|---|
| 收益 | 4 | 打通设计到开发文档/代码链路 |
| 复杂度 | 3 | 可按格式逐步扩展 |
| 风险 | 2 | 以纯导出功能为主，回归可控 |
| 可逆性 | 5 | 独立模块，易回退 |

## 验收口径（评估 DoD）
- 明确首期导出格式优先级（建议 Markdown + 1 种 ORM）。
- 明确导出字段映射规则与数据库差异处理原则。
- 明确导出产物命名、下载/复制交互方案。
- 输出是否进入开发与分期建议。

## 下一步决策项
- Go：首期格式与规则已可执行。
- Hold：先补类型映射一致性验证。
- Drop：若当前阶段不考虑导出链路拓展。
