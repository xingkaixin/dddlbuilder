## 1. 目标与边界

### 1.1 目标
在不影响现有功能稳定性的前提下，按批次完成架构整改，逐步解决评估报告中的 P0/P1 问题，提升可维护性、可测试性和可扩展性。

### 1.2 本计划覆盖范围
- 架构与代码质量整改（主线）
- 与架构整改强相关的跨领域约束（安全、性能、可访问性）
- 每批次的验收标准、回滚策略、里程碑

### 1.3 本计划暂不覆盖
- 一次性重写全部模块
- 中长期（3-6 个月）全部高级优化项的完整实现
- 与当前整改目标无关的功能扩展

## 2. 基线快照（实施前）

### 2.1 来自评估报告的关键问题
- 主组件体量过大（`src/components/App/index.tsx`）
- 状态管理分散，缺少统一机制
- 对话框逻辑重复，Props drilling 严重
- 缺乏统一错误处理边界

### 2.2 当前代码核对结果（2026-02-09）
- `src/components/App/index.tsx`: 1979 行
- 主组件 `useState` 数量: 25（报告中记录为 42，存在版本差异）
- `console.error` 仍有 2 处
- `src/stores` 目录尚未建立

## 3. 执行原则

1. 小步快跑: 每批次只解决一类核心问题，避免大爆炸改造。
2. 最小改动: 优先新增抽象层，不先大规模删除旧实现。
3. 可回归: 每批次必须通过 `bun run lint`、`bun run test:run`。
4. 可回滚: 每批次具备明确回滚点（按模块回退，不影响其他批次）。
5. 可度量: 每批次结束更新指标（行数、重复率、状态集中度、测试结果）。

## 5. 跨评估约束（来自 README 的同步要求）

以下事项虽然不完全属于架构重构，但会影响整改收益，需并行纳入计划窗口:

1. 安全 P0 修复优先: URL 分享/XSS、依赖漏洞治理。
2. Bundle 优化需尽早开始: 优先 SQL Parser 动态导入。
3. 可访问性整改放在架构稳定后集中推进: ARIA、键盘导航。

建议执行方式:
- 以“主线批次 + 并行小批”推进，不阻塞架构主线。
- 安全修复可穿插在批次 1-2，性能优化可穿插在批次 2-4。
