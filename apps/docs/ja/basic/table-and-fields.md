# テーブルとフィールドの構成

## これは誰に向けたものですか

すでにエディタ ページを表示していて、テーブルを「空白」から「DDL 対応」にしたいユーザー向け。

## これで解決すること

テーブル レベルとフィールド レベルの入力を 1 つの画面で完了し、すぐにレビューできるテーブル スキーマのドラフトを作成できます。

## ステップ

1. 「テーブル構成」で、必要に応じて `Schema Name` を、`Table Name`、`Table Comment`、および `Database Type` とともに入力します。結果: システムはターゲット データベース構文を使用して後続の SQL を生成します。 `Schema Name` が空でない場合、テーブル オブジェクトは `schema.table` として出力されます。
2. 「フィールド」に、`Field Name`、`Comment`、および `Type` を行ごとに入力します。結果: 基本フィールド構造が右側の DDL にリアルタイムで表示されます。
3. フィールド ルールに基づいて、`Nullable`、`Default Kind`、`Default Value`、および `On Update` を構成します。結果: 制約とデフォルトの動作が SQL に書き込まれます。
4. 論理列挙型を構成する場合は、フィールド行内で列挙型エディタを展開し、列挙型項目を追加し、色の識別子を設定し、ドラッグして順序を変更します。結果: このフィールドには、チームのコラボレーション中に統一された値の仕様のための列挙型メタデータが含まれます。
5. 一括フィールド入力には、ツールバーの `Add Rows` を使用します。キー列を表示し続けるために必要な場合は `Freeze` を有効にし、小さな画面での情報密度を高めるには `Compact Layout` に切り替えます。結果: 大きなテーブルの編集が高速になり、水平スクロールでエラーが発生しにくくなります。
6. フィールドを再利用するには、`Apply Template` を使用して既存のテンプレートを選択するか、現在のフィールドをテンプレートとして保存します。結果: 同様のテーブルで、標準化されたフィールド セットをすぐに再利用できます。
7. ボリュームを見積もるには、`Estimate Size` をクリックして、予想される行数を調整します。結果: 実際の物理使用量に近い、インデックス ボリュームを含む行ごとの推定サイズと合計サイズの推定値が得られます。
8. 設計標準を確認するには、`Schema Lint` パネルを開きます。結果: システムは、組み込みの命名規則と型ルールに照らして現在のテーブル構造をスキャンし、潜在的な問題を強調表示します。
9. テスト データをすばやく入力するには、`Mock Data` をクリックしてフィールド タイプごとにサンプル データを生成し、エクスポートします。結果: 開発およびテスト段階で、構造に準拠したデータを迅速に取得できます。
10. テーブルの関係を確立するには、`Foreign Key Configuration` に手動で入力するか、最初にソース テーブルとターゲット テーブルを保存し、`ER Diagram` のフィールド ハンドル間をドラッグして、ウィザードのカーディナリティ、オプション性、参照アクション、およびインデックスを確認します。結果: システムは外部キー制約 DDL を生成し、ER 図に関係を表示します。

## いつ完了するか

- フィールド リストにはこのテーブルのコア フィールドが含まれており、各行には完全なフィールド情報が含まれています。
- 右側の DDL はフィールドの変更に応じてリアルタイムで更新され、空の構造はありません。
- `Schema Name` が使用されている場合、右側の SQL には修飾されたテーブル名がすでに表示されています。
- テンプレートが使用されている場合、テンプレート フィールドは現在のテーブルに正常に適用されます。
- 列挙型が構成されている場合、列挙型項目は保存され、色の識別子は期待どおりになります。
- スキーマ lint パネルにエラーレベルの問題が表示されないか、警告が認識されます。

## よくある落とし穴

- 重複したフィールド名または予約されたキーワードは、警告をトリガーします。続行する前に、まず名前を変更してください。
- `Schema Name` が空の場合、生成では元のベア テーブル名の動作が維持されます。テーブル フィールドはテーブル名のみとして保持し、`schema.table` を混合しないでください。
- フィールドタイプを設定せずにフィールド名のみを入力すると、構造情報が不完全になります。
- 大規模な貼り付け操作の後、位置ずれを避けるために、列ごとに「デフォルトの種類」と「更新時」をスポットチェックします。
- 既存のフィールド タイプを変更するときに、システムがデータ互換性のリスク (切り捨て、精度の損失など) を警告する場合は、続行する前に現在のデータベースに既にデータがあるかどうかを確認してください。
- 外部キーを構成する場合、関連するフィールド タイプに互換性がある必要があります。そうしないと、生成された外部キー DDL がターゲット データベースで失敗する可能性があります。
- ER リレーションシップ ウィザードでは、ターゲット フィールドは単一列の主キーまたは一意のキーである必要があります。 1 対 1 の関係には、ソース フィールドに対する一意の制約も必要です。
