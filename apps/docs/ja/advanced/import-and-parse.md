# SQL のインポートと解析

## これは誰に向けたものですか

既存の SQL または構造化データ ファイルがあり、空の入力から開始するのではなく、現在の構造から進化させたいユーザー向け。

## これで解決すること

外部 SQL または構造化データ ファイルを編集可能な構成にすばやく変換し、増分設計を継続して繰り返し入力を減らすことができます。

## 前提条件

- ソース データの正しいデータベース タイプを特定しました。
- SQL テキストまたはファイルはアクセス可能であり、システムがサポートする長さ/サイズの範囲内にあります。

## ステップ

### SQL インポート

1. 上部バーの「`Import SQL`」をクリックします。結果: インポート ダイアログが開き、`Validate` ステップに入ります。
2. `Source Database` で、正しいデータベース タイプを選択し、SQL を貼り付けます。結果: システムはその方言で解析します。
3. 「`Next`」をクリックして検証を完了します。結果: パスすると、`Preview` に入ります。失敗すると、エラー メッセージと場所の詳細が表示されます。
4. `Preview` で、フィールド、インデックス、および権限付与者を検査します。必要に応じて、フィールドの順序を調整するか、不要なフィールドを削除します。結果: インポート内容は最終適用前に確認されます。
5. `Confirm`を入力してインポートを実行します。結果: 解析された結果が現在のワークスペースに書き込まれます。ソース SQL にスキーマが含まれている場合、システムはそれを `Schema Name` とベア `Table Name` に分割し、編集を続行して新しい SQL を生成できます。

### バッチ SQL インポート

1. インポートダイアログで、複数の SQL ステートメント (複数の CREATE TABLE など) を貼り付けます。結果: システムはすべてのテーブル構造を認識します。
2. プレビューで、各テーブルの解析結果と競合を確認します。結果: 重複するテーブル名またはフィールド名が存在する場合、システムは競合をマークし、マージ戦略オプションを提供します。
3. マージ戦略 (上書き、スキップ、名前変更) を選択し、インポートを実行します。結果: 複数の SQL ステートメントが戦略に従って順次適用され、バッチ移行コストが大幅に削減されます。

### CSV / Excel / JSON スキーマのインポート

1. 上部の `Import Data` をクリックし、ファイルの種類 (CSV、Excel、または JSON スキーマ) を選択します。結果: 対応するファイル セレクターが開きます。
2. ファイルをアップロードし、エンコードと区切り文字を確認します（CSV/Excel）。結果: システムはファイルの内容を解析し、フィールド名とタイプを抽出します。
3. プレビューで、自動認識されたフィールド タイプを確認し、必要に応じて手動で調整します。結果: 型マッピングは、ターゲット データベースの規則とよりよく一致します。
4. インポートを確認します。結果: フィールド構造が現在のワークスペースに書き込まれます。インデックス、権限、外部キー構成を引き続き追加できます。

## サポートされるステートメントとファイル スコープ

- SQL: `CREATE TABLE`、`CREATE INDEX`、`ALTER TABLE`、`GRANT`
- CSV: 最初の行はフィールド名として、後続の行はデータとして。システムはデータ内容から型を推測します
- Excel: `.xlsx` および `.xls` をサポートします。最初の行をヘッダーとして自動的に認識します
- JSON スキーマ: 標準の JSON スキーマ形式をサポートします。 `properties` のフィールドはテーブル フィールドとして解析されます

## いつ完了するか

- インポート後、テーブル名、フィールド、インデックス、権限付与対象者が現在のワークスペースに表示されます。スキーマが存在する場合、`Schema Name` も正しく入力されます。
- 右側の DDL および DCL 出力は空ではなくなり、予想される構造と一致します。
- インポートされた結果に基づいて段階的な調整を続けることができます。

## よくある落とし穴と障害の処理

- 方言の不一致: 同じ SQL でも、データベースの種類が異なると解析方法が異なる場合があります。まず `Source Database` を変更して、再試行してください。
- 古い SQL がオブジェクト名を `schema.table` として保存する場合、システムはそれを `Schema Name + Table Name` に分割しようとします。インポート後の分割結果を確認します。
- SQL が長すぎます: 制限を超えると直接失敗します。インポート前にコアのテーブル作成セグメントに分割します。
- 解析失敗: 最初に最小限の再現可能なセグメントを保持し、次にステートメントを少しずつ追加して問題のある部分を特定します。
- 有効なテーブル構造が認識されません。通常は、キー テーブル ステートメントの欠落または不完全な構文が原因で発生します。まず `CREATE TABLE` 本体を確認してください。
- CSV/Excel タイプの推論の偏差: 自動推論はサンプリングされたデータに基づいています。日付と金額は簡単に誤認されます。インポート後に列ごとにチェックします。
- JSON スキーマのネストされた複雑さ: 深くネストされたオブジェクトまたは配列型は、フラット テーブル フィールドに直接マッピングされない場合があります。インポート前にスキーマを簡素化します。

## トラブルシューティング

- SQL ダイアレクトの違いが大きい場合は、最初にデータベース タイプの選択を確認してください。
- 複雑な式の場合は、最初にステートメントを最小化してから、段階的にインポートして問題を特定します。
・ ファイルのインポートに失敗した場合は、ファイルのエンコードがUTF-8か、Excelファイルがパスワードで保護されているかを確認してください。
