# SQL クエリのビジュアル設計と業務テーブルのモデリング

結合クエリの作成、業務テーブル一式の作成、フィールドの依存関係の確認を行うときは、ヘッダーの「データベースツール」を開きます。これらのツールは既存のテーブル構造を使います。利用者のデータベースへの接続や SQL の実行は行いません。

## ビジュアルクエリ設計

同じ方言の MySQL または PostgreSQL の通常テーブルに対応します。入力には、保存済みテーブル、構造スナップショット JSON、厳密に解析した SQL を使えます。SQL を入力した場合は既存の解析サービスに送信されます。クエリ条件はブラウザー内で処理します。

1. 「クエリ設計」を開き、使うテーブルと基点テーブルを選びます。
2. 「結合を追加」で物理外部キーまたは論理リレーションを選び、INNER または LEFT を選びます。複合リレーションでは ON 条件をすべて生成します。関係が複数ある場合は、どれを使うかを自分で選びます。
3. 出力フィールドを追加します。COUNT、SUM、AVG、MIN、MAX、または COUNT(*) を選び、別名を設定できます。
4. AND の絞り込み条件、GROUP BY、出力列の並び順、LIMIT（1〜10000）を追加します。集計クエリでは、集計しない出力フィールドをグループ化する必要があります。
5. SQL をコピーまたはダウンロードし、パラメーター JSON をダウンロードします。MySQL は `?`、PostgreSQL は `$1`、`$2` を使います。パラメーターは順番どおりに文字列として保持されます。

例えば、ユーザーと注文の関係を選ぶと、ユーザー名と注文金額の SUM を出力し、ユーザー名でグループ化できます。文字列の比較には LIKE を使います。NULL には IS NULL / IS NOT NULL を使い、これらはパラメーターの位置を使いません。

SQL は実行されません。パラメーターは自分のプロジェクトのデータベースドライバーでバインドし、アプリケーションの必要に応じて型を変換してください。初版では、自己結合、循環結合、サブクエリ、UNION、任意の SQL 式に対応していません。入力元を変更すると設計はクリアされます。ダイアログを閉じた場合や、ツールまたはアカウントを切り替えた場合は、設定し直す必要があります。

## 複数テーブルの業務モジュール

「業務モジュール」には、編集を続けられる 3 つのひな形があります。

| モジュール | テーブル | 設計上の前提 |
| --- | --- | --- |
| ユーザーと権限 | users、roles、permissions、user_roles、role_permissions | 基本的な RBAC。権限の判定はアプリケーションが行います。テナント分離、ロールの継承、パスワード管理は含みません |
| リソース予約 | resources、slots、bookings | 1 つの時間枠につき予約レコードは最大 1 件。キャンセル後に再予約する場合は、そのレコードを更新します。時間枠の重複と同時実行のルールはアプリケーションが処理します |
| 在庫管理 | products、warehouses、stock、stock_movements | 商品と倉庫の組み合わせは一意。残高と履歴は、アプリケーションが同じトランザクションで更新する必要があります。在庫が負にならないことは自動では保証しません |

1. モジュール、MySQL/PostgreSQL、テーブル名の接頭辞、主キーの方式を選びます。
2. 接頭辞は空欄にするか、英小文字で始まる 20 文字以内の英小文字、数字、アンダースコアで指定します。接頭辞は、テーブル、インデックス、外部キーの参照に同時に適用されます。
3. 整数の方式では自動採番の主キーを使います。文字列の方式では varchar(36) を使い、値はアプリケーションが指定します。
4. テーブルを展開してフィールドと関係を確認し、CREATE TABLE の SQL または構造スナップショットをダウンロードします。
5. 「ワークスペースにまとめて保存」をクリックします。保存に成功したら、通常の手順で各テーブルを開き、編集して保存できます。

同名のテーブルがすでにある場合、グループ全体の保存が失敗します。一部のテーブルだけを飛ばしたり、既存のテーブルを上書きしたりはしません。接頭辞を変えて再試行してください。保存した内容は、現在のワークスペースの永続化と同期の方式に従います。テストデータを作る場合は、保存後に「関連テストデータ」でグループ全体のテーブルを選び、業務ルールを別途設定します。

## SQLite / Cloudflare D1

メインエディターのデータベース選択で **SQLite / D1** を選び、フィールド、主キー、インデックス、外部キーを設定して保存します。D1 は SQLite の方言を使います。Cloudflare のトークンを DDLBuilder に渡す必要はありません。

- 一般的な整数と真偽値は INTEGER、日付・JSON・文字列は TEXT、浮動小数点は REAL、バイナリーは BLOB、正確な小数は NUMERIC に対応付けます。SQLite の型親和性は、長さ、小数の精度、JSON の妥当性を保証しません。これらの要件はアプリケーションで処理してください。
- 自動採番には、昇順の INTEGER 主キーが 1 つ必要です。複合主キーや整数以外の主キーは自動採番にできません。
- 主キー、一意制約、物理外部キーは CREATE TABLE に書き込みます。通常のインデックスと一意インデックスは別の文で作成します。論理リレーションはデータベースの制約になりません。
- デフォルト値は定数と CURRENT_TIMESTAMP に対応します。任意のデフォルト式、データベースの UUID デフォルト関数、ON UPDATE、スキーマをまたぐ参照、パーティション、シャーディングには対応しません。
- テーブルとフィールドの説明は SQL コメントとして出力します。論理列挙は自動では CHECK 制約になりません。

### 初期化プロジェクト一式をエクスポートする

1. 「データベースツール」を開き、「SQLite / D1 エクスポート」を選びます。
2. エクスポート先として SQLite または Cloudflare D1 を選び、保存済みの SQLite テーブルを選ぶか、構造スナップショットをアップロードします。外部キーが参照する親テーブルはすべて選んでください。参照先が欠けている場合や、テーブル名・インデックス名が重複している場合は、エクスポートできません。
3. `0001_init.sql`、`schema.ts`、利用手順をダウンロードします。
4. 空の SQLite データベースで SQL を実行します。接続では `PRAGMA foreign_keys = ON` を有効にする必要があります。

D1 へのエクスポートでは、1 テーブルあたり最大 100 列、SQL 1 文あたり最大 100,000 バイトを確認し、上限を超えるとエクスポートを中止します。単体の SQLite には、この D1 の制限を適用しません。プラットフォームの制限の全体は [D1 limits](https://developers.cloudflare.com/d1/platform/limits/) を参照してください。

D1 を使う場合は、SQL を自分のプロジェクトの migrations ディレクトリーに置き、まずローカルで検証します。

```sh
wrangler d1 migrations apply <データベース名> --local
```

Drizzle ファイルは `drizzle-orm/sqlite-core` を使い、列、主キー、一意キー、インデックス、外部キーを保持します。`drizzle-orm` をインストールしてから、自分のプロジェクトに配置してください。TypeScript のプロパティ名はエスケープされ、SQL の名前は列定義に保持されます。初版では、主キーと一意制約の DESC 並び順に対応していません。降順の一意性が必要な場合は、一意インデックスを使ってください。

SQL と Drizzle は同じ初期構造を表します。重複して作成しないよう、マイグレーションの入力元はどちらか一方にしてください。メインエディターでも単一テーブルの Drizzle を出力できます。他のテーブルへの外部キーがある場合は、一括エクスポートを使ってください。

現在、SQLite の SQL インポート、自動 ALTER / ロールバック、権限スクリプト、ストアドプロシージャ、容量の見積もりには対応していません。初期化のエクスポートにビューは含まれません。メインエディターは CREATE VIEW だけを生成します。既存のデータベースには、移行を別途設計する必要があります。[D1 migrations](https://developers.cloudflare.com/d1/reference/migrations/)、[SQLite の CREATE TABLE 構文](https://www.sqlite.org/lang_createtable.html)、[Drizzle の制約](https://orm.drizzle.team/docs/indexes-constraints)も参照してください。

## フィールドの影響分析

1. 「影響分析」を開き、同じ方言のテーブル群を選びます。保存済みテーブルを読み込むので、先に編集内容を保存してください。
2. 対象テーブルと、変更する予定のフィールドを選びます。
3. 主キー/インデックス、入方向と出方向のデータベース外部キー、業務上の論理リレーション、MySQL パーティション、Citus 分散カラム、Hive パーティション列とクラスタ列を確認します。
4. 後の変更作業に使う Markdown レポートをダウンロードします。複合キーと関係は、フィールドの組全体として表示されます。

レポートには、確認したテーブル数、除外したビュー、範囲外の関係が表示されます。確認するのは、現在のモデル内の直接の依存関係だけです。ビューの SQL は解析せず、アプリケーションコードも調べません。インポートしていないオブジェクトも検出できません。依存関係が見つからなくても、変更が安全とは限りません。範囲をすべて選び、外部の利用箇所を確認してください。選択を変更すると、以前のレポートはすぐに無効になります。このツールは、名前の変更、削除、制約の調整を自動では行いません。
