# SQL のテーブル構造比較とデータ辞書の出力

既存のデータベースの引き継ぎ、2 つの環境の構造の確認、関連テストデータの準備には、ヘッダーの「データベースツール」をそのまま使えます。空のワークスペースにも入口があります。ログインや事前のテーブル作成は不要です。

## 入力の準備

データ辞書と関連テストデータでは、次の 3 種類の入力元を使えます。

- **保存済みテーブル**：現在のワークスペースの保存済みバージョンを読み込みます。先に編集を保存し、「再読み込み」をクリックしてから、必要なテーブルにチェックを入れます。
- **構造スナップショット JSON**：データ辞書から出力したファイルをアップロードします。フィールド ID と標準の業務要約を含みます。
- **SQL**：データベースを選び、SQL を貼り付けるか `.sql` / `.txt` ファイルをアップロードして、「SQL を解析」をクリックします。入力ごとに最大 50000 文字です。

SQL は既存の解析サービスに送信されます。解析結果は今回のツールでだけ使い、ワークスペースには書き込みません。ツールを閉じるかアカウントを切り替えると、一時的な内容は消去されます。出力したファイルはご自身で保存してください。

これらのツールは厳密に解析します。対応するのは、完全に保持できる `CREATE TABLE`、通常の `CREATE INDEX`、主キー・一意制約・外部キーを追加する `ALTER TABLE ... ADD` です。構造のスナップショットを入力してください。`INSERT`、`SET`、`DROP`、権限文を含むデータベースのバックアップ全体をそのまま貼り付けないでください。

保持できない構文があると処理を停止します。例えば CHECK、生成列、式インデックスやプレフィックスインデックス、列レベルの REFERENCES です。外部キーと一意制約には、データベース上の実際の名前が必要です。例：`CONSTRAINT fk_order_user FOREIGN KEY (user_id) REFERENCES users(id)`。解析を通すために実際の制約を削除しないでください。対応している書き方は同等のテーブルレベルの制約に書き換え、対応していない構造には別の手順を使ってください。

## データ辞書 {#data-dictionary}

1. 「データ辞書」を選び、SQL を解析するか、保存済みテーブルにチェックを入れます。
2. 文書のタイトルを入力し、検索ボックスでテーブル名、フィールド、業務説明を探します。
3. 「Markdown を出力」または「オフライン HTML を出力」をクリックします。検索しても出力範囲は狭まりません。

辞書には、フィールドの型、NULL 可否、主キー、デフォルト値、更新ルール、コメント、論理列挙、インデックス、物理外部キー、論理リレーションが含まれます。フィールドに標準が関連付けられている場合は、現在のブラウザーの標準ライブラリにある名称、説明、単位も含めます。見つからない標準は欠落として表示します。

HTML には目次、テーブル間のナビゲーション、ローカル検索が含まれます。ブラウザーで直接開くことができ、ネットワークは不要です。参照先のテーブルにチェックが入っていないリレーションは「選択範囲外」と表示します。リレーションは一覧とリンクで示します。Markdown はリポジトリへの保存や追加の編集に向いています。

## 2 つの SQL の構造比較

初版は同じ方言の MySQL または PostgreSQL に対応します。データベース間の変換は行いません。

1. 「構造比較」とデータベースの種類を選びます。
2. 「現在の構造」と「変更後の構造」をそれぞれ入力します。片側を空にすると、空のデータベースとして扱います。
3. 「構造を比較」をクリックし、追加、削除、変更、変更なしのテーブルを確認します。
4. 削除されたフィールドと追加されたフィールドが実際には 1 回の名前変更である場合は、「フィールド名の変更を確認」で明示的に対応付けます。対応付けていないフィールドは、削除と追加のままです。
5. Markdown の比較レポートまたは移行 SQL を出力します。入力を変更すると、古い結果は消去されます。

テーブルは Schema とテーブル名で対応付けます。移行では、影響を受ける外部キーを先に削除し、テーブルとフィールドの変更を実行してから、外部キーを再作成します。手動移行が必要な変更があると、SQL はダウンロードできません。差分レポートは出力できます。

SQL の対象は、入力したスナップショットだけです。実行前に、外部依存、権限、既存データ、データベースのバージョンを確認してください。削除操作ではデータが失われます。ツールはデータベースに接続せず、スクリプトも実行しません。データベース全体のデータのロールバックも提供しません。

## 関連テストデータ

初版は MySQL または PostgreSQL のテーブル群に対応します。

1. 「関連テストデータ」を選び、子テーブルと参照先の親テーブルを一緒に選択します。
2. テーブルごとの行数と固定シードを設定します。業務上の関係に沿ってデータを作る場合は、「論理リレーションも使用する」にチェックを入れます。
3. 「テストデータを生成」をクリックし、各テーブルの先頭 5 行のプレビューを確認します。
4. 完全な INSERT SQL か、テーブルごとにまとめた JSON をダウンロードします。

ジェネレーターは親テーブルを先に生成し、親テーブルで実際に生成した値から外部キーの値を選びます。複合外部キーは組ごとコピーし、主キーと一意キーは列の組で検査します。1 対 1 の関係では、子テーブルの件数も制限します。構造、行数、シードが同じなら、同じデータを繰り返し生成できます。

対応範囲と制限：

- テーブルごとに 1–1000 行、合計で最大 10000 行、250000 個のフィールド値です。
- 一般的な整数、正確な小数、浮動小数点、文字、真偽値、日時、UUID、JSON に対応します。論理列挙も生成に使います。未対応の型はエラーになります。
- JSON では、精度を失わないように bigint と正確な小数を文字列で出力します。SQL では数値リテラルのまま出力します。
- 循環依存、自己参照、親テーブルの不足、互換性のない参照型、重なり合う外部キー、満たせない一意値の数があると、生成できません。選択範囲、行数、モデルを調整してから再試行してください。
- データは、構造が一致する空のテスト用データベースで使います。既存データは検査せず、PostgreSQL のシーケンスの現在位置も調整しません。MySQL の文字列は、既定のバックスラッシュエスケープモードを前提に出力します。

単一テーブルのデータ生成には、引き続き [Mock データと論理列挙](/ja/advanced/mock-data-and-enum) を使えます。現在のテーブルと保存済みバージョンの比較は、[差分とロールバック](/ja/advanced/diff-and-rollback) を参照してください。

## プロジェクト文書の公開

ログイン後、データ辞書の下部にある「公開と管理」で公開タイトルと閲覧範囲を入力し、「新規公開」をクリックします。既定は「自分のみ」です。「リンクを知っている人」を選ぶと、ほかの人はログインせずに閲覧できます。閲覧ページには、バージョン、更新日時、検索、リレーションのナビゲーションがあります。フィールド標準の名称、説明、単位は文書と一緒に保存されます。

更新するときは、最新のテーブル構造を選び直し、「既存の公開」で元の文書を選んでから、「現在の構造を再公開」をクリックします。URL は変わらず、バージョンが上がります。タイトルや権限だけを変更する場合は、「タイトルと閲覧範囲を保存」をクリックします。別の端末が同じバージョンを変更していた場合は、上書きを拒否します。エラーの横にある「再読み込み」をクリックし、内容を確認してから再試行してください。

「公開管理」では、既存の公開を開く、リンクをコピーする、閲覧範囲を変更する、削除する、の各操作をまとめて行えます。「自分のみ」に戻すと、ほかの人からのその後の読み込みは拒否されます。すでに開かれた内容やダウンロードされた内容は、リモートで回収できません。削除すると、提案に付いたコメントも削除されます。

1 アカウントあたり最大 100 件まで公開できます。1 件の内容は最大 512 KiB、200 テーブル、10000 フィールドです。上限を超えた場合は選択範囲を減らしてください。一部だけを保存することはありません。公開した内容は現在のワークスペースから独立しています。後から編集しても、閲覧ページは自動では変わりません。

## 構造スナップショットと更新

データ辞書で「構造スナップショットを出力」をクリックすると、JSON ファイルを取得できます。後で「構造スナップショット JSON」をデータソースに選ぶと、フィールド ID、業務説明、リレーション、標準の要約を再利用できます。ファイルは最大 2 MiB です。不明なバージョン、重複するテーブル、定義が失われる内容は拒否されます。

更新は現在、同じ方言の MySQL または PostgreSQL に対応します。

1. 「構造を更新」で、元の構造スナップショットをアップロードします。
2. 「現在のデータベース構造」で、保存済みテーブル、SQL、別の構造スナップショットのいずれかを選びます。**更新範囲をすべて選択してください**。選ばなかった古いテーブルは削除として扱います。
3. 追加 / 削除されたテーブルと、フィールド、インデックス、リレーションの差分の詳細を確認します。名前の変更は削除と追加として扱い、名前変更を自動では推測しません。
4. 比較レポートと更新後の構造スナップショットをダウンロードするか、元のプロジェクト文書を選んで再公開します。

同名のフィールドは、元のフィールド ID、業務説明、論理列挙、標準の参照を保持します。型、デフォルト値、NULL 可否、物理制約は新しい構造のものを使います。既存の論理リレーションは、両端がまだ存在する場合だけ保持します。無効になったリレーションは一覧で示します。更新結果はワークスペースに自動では書き込みません。結果のファイルを、次回の更新の基準として使ってください。

### ローカルのデータベースから構造を取得する

元のデータベースに合ったクライアントをインストールし、自分のコンピューターで次のいずれかのコマンドを実行します。アドレス、ユーザー、データベース名は置き換えてください。パスワードは、クライアントの入力プロンプトかローカルの認証情報ファイルで指定します。DDLBuilder はデータベースの接続資格情報を受け取りません。

```sh
mysqldump --host=127.0.0.1 --user=reader --password \
  --no-data --skip-add-drop-table --no-tablespaces \
  --set-gtid-purged=OFF app_database > mysql-structure.sql
```

```sh
pg_dump --host=127.0.0.1 --username=reader --dbname=app_database \
  --schema-only --no-owner --no-privileges --format=plain \
  --file=postgres-structure.sql
```

これらのコマンドが生成するのは生の構造ダンプで、**DDLBuilder にそのまま取り込めることが保証されたファイルではありません**。クライアントのエラー出力を確認し、元のファイルを残しておいてください。本ページの「入力の準備」の範囲に沿って、必要なテーブル、インデックス、名前付き制約を整理してから、厳密な解析に渡します。ダンプ内のセッション設定、権限、シーケンス、トリガーなどは別に扱う必要があります。未対応の制約を削除して、完全な構造であるかのように扱わないでください。すべての解析に成功したら、DDLBuilder の構造スナップショットを出力し、更新の基準にします。

一部のテーブルだけを選ぶ場合も、必要な親テーブルを含めてください。Schema をまたぐ依存関係は別途確認してください。クライアントのオプションは [mysqldump のドキュメント](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html) と [pg_dump のドキュメント](https://www.postgresql.org/docs/current/app-pgdump.html) に従ってください。

## 固定バージョンの変更提案

「構造比較」で比較とフィールド名変更の確認を終えたら、「変更理由」を入力し、ログインして公開を作成します。提案は、現在の構造、変更後の構造、名前変更の対応付けを固定して保存します。後で構造を調整する場合は、新しい提案を作成してください。元の提案で変更できるのは、タイトルと閲覧範囲だけです。

リンクを知っている人に公開した提案は、匿名で閲覧できます。ログインした読者は、対象の場所（例：`orders.amount`）を入力してコメントできます。コメントは提案ごとに最大 200 件、1 件あたり最大 4000 文字です。作成者は「解決済みにする」または「未解決に戻す」を選べます。コメントはテキストとして表示され、現在の固定バージョンに結び付きます。解決済みの状態は、SQL の実行を承認したことを意味しません。

読者は比較レポートをダウンロードできます。ジェネレーターのブロック項目がある場合、移行 SQL はダウンロードできません。外部からのアクセスを閉じると、ほかの人は閲覧もコメントもできなくなります。

## 業務テストシナリオを保存する

「関連テストデータ」で「業務テストシナリオ」を展開し、ルールを適用するテーブル、フィールド、生成方法を選びます。

| ルール | 入力と制限 |
| --- | --- |
| NULL の割合 | 0–100。各行で NULL を生成する確率で、少ないサンプルで正確な割合になるとは限りません。主キーと NOT NULL のフィールドは 0 にする必要があります |
| 列挙値の重み | 1 行に `値=重み` を 1 つ。例：`PAID=80`、`PENDING=20`。重みは正の数で、実際の割合はサンプルによって変動します |
| 数値範囲 | 整数または正確な小数のフィールドの閉区間。精度はフィールド定義に合わせる必要があり、幅は最小精度単位で最大 MAX_SAFE_INTEGER 個です |
| 日付範囲 | 開始日と終了日。形式は YYYY-MM-DD で、日単位で生成します |
| 日付オフセット | 同じテーブルの日付フィールド名と整数の日数。例：`created_at` に 7 日を加算。循環依存は使えません |

「フィールドルールを追加・置換」をクリックしてから生成します。物理外部キーと、有効にした論理リレーションのフィールドは親テーブルのデータで決まるため、上書きルールは使えません。一意値が足りない、型が合わない、フィールドがもう存在しない、のいずれかに当てはまると出力できません。

シナリオ名を入力すると、現在のブラウザーに保存できます。最大 50 件で、同名で上書きするときは確認があります。「保存済みシナリオを読み込む」は、ルール、シード、行数、論理リレーションのオプションを復元します。テーブルの選択は自分で行ってください。JSON のインポート / エクスポートは、ブラウザー間の受け渡しに使います。インポートするファイルは最大 512 KiB です。設定を変更したら再生成が必要です。任意のコードや SQL の式は実行できません。

## MySQL から PostgreSQL への互換性レポート

「移行互換性」を開き、MySQL のテーブルを選びます。結果は「対応候補あり」「手動確認」「範囲外」に分類され、項目ごとに元の定義、候補、次の作業を表示します。Markdown で出力できます。

検査の対象は、unsigned の範囲、自動採番、正確な小数、文字の比較、日時とタイムゾーン、JSON、列挙型、デフォルト値、ON UPDATE、インデックス、外部キー、ストレージのオプションです。ビューのクエリと不明な型は別に表示します。レポートは、実データ、アプリケーションのクエリ、実行時の挙動を検査しません。自動移行や、そのまま実行できるデータベース間のスクリプトも提供しません。
